# 16*데이터*웨어하우스*아키텍처*비교*및*빅쿼리*성능*최적화\_방법

---

## On-premise 데이터 웨어하우스 특징

- 말 그대로 기업 내부의 데이터 웨어하우스 서버와 인프라를 직접 구축하고 운영하는 방식
- 즉, 모든 **하드웨어·소프트웨어·보안·유지보수**를 기업 자체 IT팀이 직접 관리하는 구조
- 완전한 제어권이 있고, 높은 보안성이 특징이며,
- 비용이 크게 발생하고, 데이터 증가에 따른 유연한 확장이 어려움
- 금융기관, 정부기관, 국방부분 등에서 실제 사용됨

<BR>

## Cloud 데이터 웨어하우스 특징

- 데이터 저장·처리 인프라를 클라우드 서비스 제공자가 호스팅(AWS, Azure, GCP...)가 호스팅하고, 사용자는 인터넷을 통해 접근하여, 관리·분석하는 방식
- 쉽게 말해서 **데이터 웨어하우스를 서비스처럼 사용하는 구조**
- `Google BigQuery` / `Amazon Redshift` / `Snowflake` / `Azure Synapse Analytics` 등이 존재
- 초기 인프라 투자 비용이 거의 없으며, 확장성과 유연성이 우수하다는 장점이 존재
- 하지만 데이터 외부 전송이 제한되고 쿼리 과다 실행 시 요금이 급증하는 구조임

<BR>

## Serverless 데이터 웨어하우스 특징

- 서버를 직접 관리하지 않는(Server-less) 방식
- 사용자는 서버나 클러스터를 신경쓰지 않고, 오직 쿼리 실행과 데이터 분석에만 집중할 수 있음
- 데이터 저장, 확장, 인프라 프로비저닝(서버, 네트워크, 스토리지같은 IT자원 미리 준비하는 과정),
- 리소스 할당, 백업 장애 복구 등은 모두 **클라우드 제공자가 자동으로 관리**
- `Google BigQuery` / `AWS Athena` / `Azure Synapse Serverless SQL Pool` 등이 존재
- 서버 관리가 불필요하여 개발 생산성이 향상되고 자동으로 확장/자원 최적화가 이뤄져 비용이 효율적이지만,
- 성능 제어가 어려우며 이것 역시 쿼리량이 많거나 비효율적인 쿼리 구조일 경우 비용이 급증

## BigQuery에서 쿼리 성능 최적화 방법

- 기본 원칙은 쿼리는 작업을 덜 하도록 설계하는 것이 목적
- 이를 위해 다양한 기법들이 존재

| 최적화 기법                      | 방법                                           | 핵심 포인트                                            | 예시 / 비유                                               |
| -------------------------------- | ---------------------------------------------- | ------------------------------------------------------ | --------------------------------------------------------- |
| **파티셔닝 (Partitioning)**      | **큰 테이블을 날짜·ID 단위로 쪼개 저장**       | 쿼리할 때 필요한 “부분만” 읽어서 속도가 훨씬 빨라짐    | 책 1,000권 중 **이번 달만 읽기**처럼 필요한 구간만 열람   |
| **클러스터링 (Clustering)**      | **비슷한 값끼리 묶어 저장**                    | 필터나 조인할 때 관련 데이터가 몰려 있어서 빠르게 찾음 | 도서관에서 **장르별로 정리된 책장** 덕분에 찾기 쉬운 느낌 |
| **SELECT \* 피하기**             | **필요한 컬럼만 조회하기**                     | 불필요한 데이터 읽지 않아 속도 빠르고 비용 절감        | 필요한 문장만 복사하기, 전체 문서 복사하지 않기           |
| **필터 먼저 적용하기**           | **WHERE 조건으로 미리 걸러서 조인하기**        | 처리해야 할 데이터가 줄어들어 쿼리 부하 감소           | 음식 만들기 전에 **재료 다듬고 불필요한 건 버리는 과정**  |
| **머티리얼라이즈드 뷰 활용하기** | **자주 쓰는 복잡한 쿼리 결과를 미리 저장**     | 매번 계산 안 해도 바로 결과 확인 가능                  | 매일 아침 계산하지 않고 **어제 결과표 미리 써두는 것**    |
| **캐시(Cache) 사용하기**         | **같은 쿼리를 또 실행하면 저장된 결과 재사용** | 반복 쿼리 속도↑, 비용↓                                 | “어제 검색한 결과”가 메모리에 남아 바로 열리는 느낌       |
| **쿼리 구조 단순화하기**         | **불필요한 중첩, 중복 쿼리 제거**              | BigQuery가 처리해야 할 단계가 줄어듦                   | 미로처럼 꼬인 길 대신 **직선 도로로 가는 느낌**           |
| **슬롯(Slot) 관리하기**          | **쿼리에 할당된 컴퓨팅 자원(슬롯)을 조정**     | 슬롯을 충분히 확보하면 대기 없이 즉시 실행 가능        | 셰프(슬롯)가 많으면 요리가 동시에 빨리 끝남               |
